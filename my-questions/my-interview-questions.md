Набор вопросов, по которому удобно собеседовать кандидата (или проверять себя). Под каждым вопросом — что ожидается в ответе и ссылка на подробный разбор.

## Общее
- **Расскажи про свой опыт.** Ожидается: роль, стек, домен, 1–2 достижения с цифрами, что делал кроме кода.

## Java

- **Объясни `public static void main(String[] args)`.** Точка входа JVM: `public` — доступен JVM, `static` — без создания объекта, `void` — результат не нужен, `args` — аргументы командной строки. Плюс: с Java 25 можно `void main()` без `static` и параметров. → [java-core](../java-core.md#10-public-static-void-mainstring-args)
- **В чём особенность generics?** Проверка типов при компиляции, стирание в рантайме до границы типа, следствия (нельзя `new T()`, `instanceof List<String>`), PECS. → [java-core](../java-core.md#8-generics)
- **Отличия абстрактного класса от интерфейса.** → [java-core](../java-core.md#6-интерфейс-и-абстрактный-класс)
- **Если бы в Java не было множественной реализации интерфейсов, к какой проблеме это привело бы?** Интерфейсы разрастались бы (нарушение ISP) или дублировался бы код; нельзя было бы дать классу несколько независимых ролей.
- **Обработка исключений, когда `finally` не выполнится?** → [java-core](../java-core.md#5-исключения)
- **GC в Java: какой по умолчанию, общий принцип, GC roots?** G1; трассировка достижимости от корней; корни — локальные переменные и параметры в стеках всех живых потоков, статические поля, JNI-ссылки, мониторы. → [jvm](../jvm.md#2-сборка-мусора-gc)
- **Объясни стримы. Для чего `flatMap`?** Ленивая цепочка промежуточных операций и одна терминальная; `flatMap` превращает каждый элемент в стрим и склеивает (1 → N). → [java-core](../java-core.md#11-stream-api)
- **`List.of()` — особенности?** Неизменяемый, не допускает `null`; `add()` бросает `UnsupportedOperationException` — формально спорно с точки зрения LSP, это «необязательные операции» коллекций Java. → [java-core](../java-core.md#15-короткие-ответы-на-частые-вопросы)
- **Локальная `int x = 5`, на следующей строке используется в лямбде стрима — что будет? А если потом `x++`?** Работает: `x` effectively final. С `x++` — ошибка компиляции: лямбда захватывает копию значения, переменная должна быть фактически неизменяемой. → [java-core](../java-core.md#функциональный-интерфейс)
- **Объясни `record`. В чём минусы?** `final`, неизменяемые поля, генерируются конструктор, аксессоры, `equals`/`hashCode`/`toString`. Минусы: нельзя наследовать класс, неизменяемость поверхностная, **нельзя использовать как JPA-сущность** (Hibernate нужны конструктор без аргументов, изменяемость и прокси). Для DTO и проекций Spring Data — отлично. → [java-core](../java-core.md#record)

### `@Transactional`
- **Где нужно использовать?** На сервисных методах — единицах бизнес-операции. Для методов только чтения — `readOnly = true` (нет dirty checking и flush). Не держать внутри транзакции внешние вызовы. → [spring](../spring.md#7-transactional)
- **Создастся ли новая транзакция? Как решить проблему?**

```java
@Service
@RequiredArgsConstructor
public class TestService {
    private final TestRepository repository;
    private final TestEventPublisher eventPublisher;

    @Transactional
    public void test1() {
        repository.save(new Test());
        test2();
    }

    @Transactional(propagation = Propagation.REQUIRES_NEW)   // сначала спросить без этой строки
    public void test2() {
        eventPublisher.sendEvent("Test saved");
    }
}
```

Ожидается: вызов через `this` идёт мимо прокси, новой транзакции не будет. Решения: вынести в другой бин или фасад, `TransactionTemplate`, self-injection через `@Lazy`/`ObjectProvider`. Следующий вопрос — а нужно ли вообще отправлять событие внутри транзакции? → outbox. → [spring](../spring.md#задача-создастся-ли-новая-транзакция)

## Паттерны микросервисов
- **Transactional outbox. Как обеспечить согласованность между сохранением в БД и отправкой события?**

```java
    private final TestService service;

    public void create(Order order) {
        service.test1();

```

- **Circuit breaker.** Один сервис регулярно запрашивает второй, тот делает долгие расчёты. Второй начал тормозить или упал, первый продолжает слать запросы и ждать ответа, его потоки заканчиваются. Как решить? Ожидается: таймауты, circuit breaker (Closed → Open → Half-open), bulkhead, fallback; библиотека Resilience4j (Hystrix больше не развивается). → [microservices](../microservices.md#устойчивость-таймауты-retry-circuit-breaker)

## Hibernate и БД
- **Как улучшить код?**

```java
for (int i = 0; i < objectList.size(); i++) {
    repository.save(objectList.get(i));
}
```

Ожидается: одна транзакция на всю пачку (`@Transactional` или `saveAll`), включить `hibernate.jdbc.batch_size` + `order_inserts`, генерация id через `SEQUENCE` (с `IDENTITY` батчи не работают), для больших объёмов — `flush`/`clear` или JDBC batch. → [hibernate](../hibernate.md#7-генерация-id-и-пакетная-вставка)

- **Объясни N+1.** → [hibernate](../hibernate.md#4-проблема-n1)
- **Уровни изоляции. Какой по умолчанию в PostgreSQL?** Read Committed. → [databases](../databases.md#3-уровни-изоляции)
- **В транзакционном методе `repository.save(obj)`, а на следующей строке `obj.setName("newName")`. Что сохранится?** Если `obj` новый (`persist`) или загружен в этой транзакции — `"newName"`: dirty checking при flush перед коммитом. Если `obj` был detached и `save` сделал `merge` — изменён не тот объект, в БД останется старое значение; работать нужно с объектом, который вернул `save`. → [hibernate](../hibernate.md#dirty-checking-и-flush)
- **SQL-инъекции.** Возникают при склейке ввода с текстом запроса — в любой технологии (JDBC `Statement`, конкатенация в JPQL и native query). Пример: `"SELECT * FROM users WHERE name = '" + name + "'"` и `name = "x' OR '1'='1"`. Защита — параметры (`PreparedStatement`, `:param`): данные передаются отдельно от SQL и никогда не становятся кодом. → [databases](../databases.md#13-sql-инъекции)
- **Индексы: когда применяем, когда избегаем?** → [databases](../databases.md#5-индексы)
- **Почему этот запрос не годится для прода и как переделать?**

```sql
SELECT call_id, process_log_id, phase
FROM process_log
WHERE lower(status) = 'running';
```

Ожидается: функция над колонкой не даёт использовать обычный индекс (Seq Scan); решения — хранить статус в одном регистре и писать `status = 'RUNNING'`, индекс по выражению `lower(status)` или частичный индекс `WHERE status = 'RUNNING'`; нет `LIMIT`. PostgreSQL сравнивает строки с учётом регистра, `LIKE` не быстрее `=`. → [databases](../databases.md#пример-с-собеседования-почему-запрос-плохой-для-прода)

- **Способы масштабирования БД.** → [databases](../databases.md#9-масштабирование)
- **Пагинация: offset и keyset, когда что?** → [databases](../databases.md#8-пагинация-offset-vs-keyset-seek)

### Задача на проектирование: сервис уведомлений

Компания продаёт товары и услуги. Нужно реализовать логику в сервисе уведомлений. Из Kafka приходят сообщения о заказах (`OrderMessage`). В зависимости от смены статуса заказа отправляются разные push-уведомления, в одно или несколько мест. Реализовать одно уведомление. Если уведомление не отправлено — переотправить. Аналитики предупредили, что видов уведомлений будет становиться больше, это нужно предусмотреть.

Пример: заказ перешёл из оплаченного статуса в отменённый, и с создания заказа прошло не более 30 минут — отправить покупателю уведомление о произошедшем.

Цель — показать всесторонние навыки. По задаче можно и нужно задавать вопросы, комментировать свои шаги.

Разбор — [system-design](../system-design.md#пример-1-сервис-уведомлений-по-статусам-заказов).
